# Kobold review

Four defects confirmed. All four share a shape: **a failure the code already knows how to describe gets reported as a success or as the wrong failure.** For a driver glancing at a mounted phone, that is the worst possible class of bug — the screen is confidently wrong, and the wrongness sends them to fix something that isn't broken.

Ranked by what it costs the person in the car.

---

## 1. Correctness — Diagnostics shows a green tick for a read that never happened

**Defect:** `read()` lands on `.ready` unconditionally, so a pass in which every request threw renders "No trouble codes ✓".

`App/DiagnosticsModel.swift:89`

```swift
        state = .ready
        logSummary()
```

**Failure.** Adapter asleep, or the BLE link drops mid-read. `ELM327Driver.sendRaw` throws `.notConnected` (`Sources/KoboldCore/ELM327/ELM327Driver.swift:711-713`), so modes 03/07/0A all throw. The three helpers at `DiagnosticsModel.swift:123-152` swallow every error into `unavailable` and return `[]`. `read()` still sets `.ready`, `hasAnyCodes` is false, and `VehicleDiagnosticsView.swift:126` renders `Label("No trouble codes", systemImage: "checkmark.circle")` — an affirmative clean bill of health built from zero answers. This is the one finding here that could plausibly stop someone investigating a real fault.

`.failed` is declared at line 19 and **never assigned** — grep shows only `.reading` (51), `.ready` (89), `.idle` (94), and `state` is `private(set)`. The `.failed` branch at `VehicleDiagnosticsView.swift:26` and its "Try again" button are dead code.

The doc comment at `DiagnosticsModel.swift:40-42` says `unavailable` exists "so the screen can distinguish 'this car does not answer that' from 'not asked yet'". Repo-wide grep finds `unavailable` **only inside DiagnosticsModel.swift**, used solely for the log line at 180. The justification is factually false as wired up — that is itself the finding.

**Smallest fix.** Count successful reads in `read()`; if zero, `state = .failed("Nothing answered — the adapter may have gone to sleep.")`. Then have `codesSection` consult `model.unavailable` so the checkmark only renders when modes 03/07/0A actually answered.

*(Correction to the filed claim: the user is not stranded — `VehicleDiagnosticsView.swift:37-41` shows a "Re-read" button in the `.ready` state. The false checkmark is the defect; the no-way-back consequence was overstated.)*

## 2. Connection — ignition-off tells the user to re-seat a healthy adapter

**Defect:** `sendLocked` converts `UNABLE TO CONNECT` into `.deviceError` before `detectProtocol`'s `catch` can see it, and that catch only matches `.timeout`.

`Sources/KoboldCore/ELM327/ELM327Driver.swift:306-308`

```swift
            case .bufferFull, .canError, .unableToConnect:
                throw ELM327Error.deviceError(command: command, reply: reply)
```

`Sources/KoboldCore/ELM327/ELM327Driver.swift:228` — `} catch ELM327Error.timeout {`

**Failure.** Ignition off, adapter fine. `ATZ`/`ATE0`/`ATSP0` all answer OK; `0100` returns `UNABLE TO CONNECT`. `.unableToConnect` is not transient (`ELM327Reply.swift:46-51`) so no retry absorbs it; `sendLocked` throws `.deviceError`; the `catch` at 228 does not match; `start()` (124-127) rethrows it unchanged. `guard probe.isData` at line 240 — which exists to produce the same verdict — is never reached.

`SessionModel.swift:713/734` switch on `.adapterSilent` and `.protocolNegotiationFailed` only, so `.deviceError` falls to `default`: the pill reads **"Adapter did not respond"** (736) — false, it answered every command — and the message reads "Check the adapter is seated and the ignition is on." (726-727), sending the driver to unplug a working dongle. `.adapterSilent` was added at `ELM327Driver.swift:11-18` precisely to stop this misdirection; this path reintroduces it in the opposite direction.

The comment at 231-233 states the intended behaviour explicitly ("the same conclusion as UNABLE TO CONNECT and deserves the same advice"), so nothing here is justified-by-comment. `AdapterDescriptor.swift:50-52` confirms the 25 s `protocolSearchTimeout` exists so the adapter *gets the chance* to say UNABLE TO CONNECT — the timeout cannot pre-empt it.

**Smallest fix.** Widen the catch:

```swift
} catch ELM327Error.timeout, ELM327Error.deviceError {
```

*(Correction: this also swallows `.canError` and `.bufferFull` on the same line — appropriate, both are vehicle-side. And the `guard probe.isData` branch stays reachable for `.ok`/`.searching`, not only NO DATA / `?`.)*

## 3. Lifecycle — a dead link fabricates 65,000 "no reply" results and permanently marks the module scanned

**Defect:** `scanIdentifiers`'s loop has no transport-liveness check, so after a disconnect every remaining address is recorded as a genuine silence at memory speed.

`Sources/KoboldCore/ELM327/ELM327Driver.swift:534-535`

```swift
        for identifier in identifiers {
            if Task.isCancelled { break }
```

**Failure.** Deep-scan Service 22; the Vgate hibernates or the car switches off. `BLETransport.didDisconnectPeripheral` → `teardown(state: .failed(...))` (BLETransport.swift:434, 314). Thereafter `sendRaw`'s `guard await transport.state == .connected` (line 711) throws before any I/O, `probe`'s `try?` returns `.silent` (530), and the `consecutiveSilences < 8` gate (548) suppresses the slow retry — so ~65,000 identifiers are consumed in seconds, each one an `await absorb(...)` MainActor hop, a `working.record`, and every 64 a full JSON re-encode of a growing `ScanProgress` (ScanModel.swift:276-279) that locks the UI.

`UDSScan.swift:170` advances `cursor[key] = identifier + 1` for each fabricated silence, so `ScanModel.remaining(for:)` (140-147) returns 0 and `DeepScanView.swift:239-248` renders the button as "Scanned" and `.disabled`. `ScanModel.reset()` exists (line 90) but grep finds **no call site in App/** — the module reads as fully swept forever.

Nothing stops it: `absorb` returns `false` only after three `refused(0x11)` (245-254), which silence never produces; a BLE drop dismisses no sheet; `SessionModel.stop()` nils `activeDriver` but the sweep holds the actor as a captured parameter; and the pump can't intervene because `scanIdentifiers` holds `acquire()` (516) for the whole sweep.

The comment at 496-497 states the opposite of what the code does: *"a dropped Bluetooth connection halfway through should cost the remaining addresses, not the ones already covered."*

**Smallest fix.** In `scanIdentifiers`, break when the transport is no longer connected — cheapest correct version is to distinguish a thrown `.notConnected` from a real timeout in `probe` and `break` on the former, rather than recording it. Secondarily, scope `finish`'s rollback per service (`ScanModel.swift:306`) instead of testing module-wide `readable`/`gated`.

*(Correction: in the drop-at-0x0100 scenario the module-wide guard isn't even what fails — any genuine `0x31` refusal in the connected prefix increments `absent`, so `heardNothing` is already false (UDSScan.swift:246), `deaf` is empty, and `finish()` skips the discard branch entirely. Same outcome, different mechanism.)*

## 4. Lifecycle / interaction — a cancelled sweep clears the state of the sweep that replaced it

**Defect:** `finish(target:)` runs on the cancelled path, and `ScanModel` has no generation token.

`App/ScanModel.swift:195-201`

```swift
        task = Task { [weak self] in
            for service in Self.services {
                if Task.isCancelled { break }
                await self?.sweep(target: target, service: service,
                                  driver: driver, onProgress: onProgress)
            }
            self?.finish(target: target)
        }
```

**Failure.** Two distinct ones.

*State corruption.* Tap Stop on module A: `stop()` (165-169) sets `isRunning = false` immediately, but the task is parked in `scanIdentifiers` and must still complete the in-flight probe plus the `ATAR` / `ATSH 7DF` restores (`ELM327Driver.swift:557-558`) — real BLE round trips, and `awaitResponse`'s continuation (753) has no cancellation handling. Meanwhile `start()`'s only guard is `guard !isRunning` (180) and `DeepScanView.swift:246` disables on the same flag, so module B's scan is now tappable. B starts, blocks in `acquire()`; A's task reaches line 200 and runs `finish(target: A)`, clearing `isRunning`/`currentTarget` while B is genuinely sweeping. B loses its Stop button (`DeepScanView.swift:234` requires `isRunning && currentTarget == key`), and a third tap overwrites `self.task` (194), orphaning B permanently uncancellable.

*False verdict.* On any user Stop, `finish` also states a conclusion for a partial run. Stop after 200 of 65,536 addresses of "does not exist" yields `lastMessage = "Every address refused... This module genuinely has no data there."` (327-328) — exactly the "reads as a completed experiment" outcome the comment at 299-304 forbids. It also runs `working.discard` (309), contradicting `stop()`'s own comment at 170-171 that progress is kept.

**Smallest fix.** Guard line 200: `if !Task.isCancelled { self?.finish(target: target) }`. Properly: give `ScanModel` the generation token `SessionModel` already uses — capture it in `start()`, bump in `stop()`, drop stale writes in `finish`/`absorb`/`publish`.

*(Correction: no data race. `acquire()` serialises adapter traffic and both tasks are `@MainActor`. The real cross-talk is that a new sweep runs `ScanModel.swift:212-215` synchronously before blocking, resetting the still-running sweep's `serviceRefusals` and `sinceSave`.)*

## Checked and clean

Examined and found to hold up, so these are not unexamined territory:

**Request/response pairing** — the desync class of bug is genuinely closed. `ELM327Driver.swift:330` (`responses.first { $0.header == expected }`) unconditionally prefers the addressed module's reply; `ResponseCountTests.swift:115-125` asserts the addressed module wins when another answers first. The `?? responses.first` fallback is load-bearing, not sloppy: `ECUResponse.header` is nil for headerless/CAF-parsed replies (`ISOTPAssembler.swift:108,141`), and throwing instead would break every read on an adapter that ignores `ATH1` — a state `runInitSequence` deliberately tolerates. `PIDDecoder.decode` (25-40) independently enforces the mode and PID echo.

**Per-signal observation** — `SignalBus`/`LiveSignal` (`SignalBus.swift:1-60`) does what its comment claims. `history` is correctly `@ObservationIgnored` so chart appends don't invalidate gauge readers. `DashboardView.body` reads **no** signal value; values are read inside `DashboardCardView`/`TachometerView`. The design is intact.

**Dashboard render path under drag** — `DashboardCardView` stores `card: DashboardCard` (Equatable), `signal: LiveSignal` (reference), `isEditing: Bool`; none change while `pull` moves, so SwiftUI memoizes the cards away. `DashboardModifiers.swift:55-58` shows the one genuinely expensive computation was already hoisted out of the body for exactly this reason, and that comment is correct.

**Reorder arithmetic** — `DashboardView.swift:490-493` telescopes exactly (`dragHome` is reassigned to the same landing each iteration), so no compensation error can accumulate regardless of what `slotFrames` holds.

**Transport liveness guard placement** — `sendRaw`'s `guard await transport.state == .connected` (711) is correctly before the write, so it costs nothing. The bug in finding 3 is that the *scan loop* ignores it, not that the guard is wrong.

**Retry/backoff semantics** — `ELM327Reply.isTransient` (46-51) correctly excludes `.unableToConnect`, `.canError`, `.bufferFull` from retry; `detectProtocol` correctly passes `retries: 0` with a comment explaining why multiplying a 25 s budget is wrong.

## Refuted — do not re-find these

1. **"`read()` decodes another module's reply when the expected header is absent"** (`ELM327Driver.swift:342`). Misreads the code: the header preference at line 330 is unconditional, not gated on `hint`. The `?? responses.first` fallback is required for headerless replies. The transFluidTemp story requires an engine Mode 21 A0 response that nothing in the repo supports.

2. **"`pull` @State re-renders the whole dashboard at touch rate"** (`DashboardView.swift:97`). Mechanism right, consequences wrong — conflates re-evaluating a parent body (cheap structs) with re-rendering children. Cards and the tachometer are memoized on unchanged stored properties. Residual cost is ~10 `GeometryReader` closures yielding `Color.clear` with unchanged frames, so `onPreferenceChange` doesn't even fire.

3. **"`SignalDisplay` rebuilt 4×/body at 10 Hz"** (`DashboardCardView.swift:136`). ~3.25 constructions per 120 Hz frame, tens of microseconds, beside ICU `FormatStyle` calls and a Canvas stroking 21 paths that the body must do anyway. Also 10 Hz is a replay-only ceiling — real half-duplex BLE gives 2-5 publishes/second (`AdaptiveTiming.swift:7-8`). No wrong number, no dropped reading. Preference, not defect.

4. **"Reorder oscillates and corrupts drag offset"** (`DashboardView.swift:483`). Arithmetically impossible (see clean list), and internally inconsistent — its own model predicts a full-slot misplacement, not the "few points" described.

### Diagnostics reports "No trouble codes" with a checkmark when the code reads failed and were never answered

`App/VehicleDiagnosticsView.swift:126` · **high** · misleading-text

`DiagnosticsModel` deliberately records which reads came back with nothing (`unavailable`, documented at DiagnosticsModel.swift:41 as existing "so the screen can distinguish 'this car does not answer that' from 'not asked yet'"), and `read()` unconditionally lands on `state = .ready` (DiagnosticsModel.swift:89) whatever happened. `codes(from:mode:label:)` swallows the throw, inserts into `unavailable` and returns `[]` (DiagnosticsModel.swift:123-130). No view in App/ ever reads `unavailable` — `grep -rn "unavailable" App/` matches only DiagnosticsModel.swift. So the failure signal is collected and then thrown away, and the screen states a clean bill of health it never obtained.

*Failure:* Driver taps "Read the car". The adapter has gone to sleep or the ignition drops mid-read, so all three of Mode 03 / 07 / 0A throw. `storedCodes`, `pendingCodes` and `permanentCodes` are all `[]`, `hasAnyCodes` is false, `state` becomes `.ready`. The screen renders `Label("No trouble codes", systemImage: "checkmark.circle")` — a tick and an all-clear — for a car whose ECUs were never heard from. The same read is what gates the P0088 fuel-pump-recall banner at line 107, so an open recall the app is specifically built to surface is silently reported as absent. Readiness, fuel system and identity sections simply vanish rather than saying they were not answered (lines 165, 214, 232 are all `if let` / non-empty guards).

*Suggested fix:* Gate the all-clear on the reads having actually succeeded: `if model.unavailable.isDisjoint(with: ["stored", "pending", "permanent"])` for the checkmark, and otherwise show a "The car did not answer — codes unknown" row. Same for the sections that disappear: an unavailable read should render a "not answered" row rather than nothing.

### textTertiary on the panel material fails the 4.5:1 the design doc mandates — and it is what labels every gauge

`App/KoboldTheme.swift:64` · **high** · contrast

docs/06-design-language.md:120 states the rule explicitly: "hold WCAG 4.5:1 (text) / 3:1 (large)". `textTertiary` over the `InstrumentPanel` face measures 3.27:1 on Midnight, 3.17:1 on Ember and 2.97:1 on Slate (computed against `surfaceRaised`, which is the top of the card's gradient — InstrumentPanel.swift:52 — exactly where the header label sits, before the specular band at line 61 lightens it further). Slate is below even the 3:1 large-text floor. Every use of it is small text: 10pt, 11pt and 12pt.

*Failure:* On a phone mounted in a G70 in daylight — the glare case docs/06:115 cites — the 10pt uppercase label naming each card ('COOLANT', 'BOOST', 'INTAKE AIR') renders at ~3.2:1 and is the first thing to wash out. The numeral above it stays legible at 14:1 (textPrimary), so the driver sees a number with no readable indication of which reading it is; two temperature tiles in the same grid become indistinguishable at a glance. The same role carries the unit symbol (DashboardCardView.swift:111, CompactGaugeView.swift:93), so 'psi' vs 'kPa' washes out with it.

*Suggested fix:* Lift `textTertiary` per theme until it clears 4.5:1 against `surfaceRaised` (Midnight needs roughly `Color(red: 0.55, green: 0.59, blue: 0.66)`), or promote the card header and unit symbol to `textSecondary`, which already measures 7.11:1 on the same surface. Re-check all three themes, and with Increase Contrast on, as docs/06:120 also asks.

### readRawPID decodes readiness/status from an arbitrary ECU's reply, without checking mode or echoed PID

`Sources/KoboldCore/ELM327/ELM327Driver.swift:654` · **high** · correctness

Requests go out functionally — the init sequence is `["ATZ", "ATE0", "ATL0", "ATS0", "ATH1"]` (ELM327Driver.swift:144) with no `ATSH`/`ATCRA`, and every non-scan path restores `ATSH 7DF`. The driver's own doc comment says so: "A functional request reaches all modules and each answers with its own capabilities — the reference car returns three responses to `0100`" (ELM327Driver.swift:669-672). `readRawPID` then takes `ISOTPAssembler.assemble(lines: lines).first` — whichever module's frame the adapter happened to print first — and feeds it straight to `response.data(pidByteCount: 1)` with no check that the payload starts `41 <pid>`. Contrast `read(_ definition:)` (line 322-327), which explicitly filters `responses.first { $0.header == expected }` because "a functional request can draw replies from several modules". `readRawPID` serves PIDs 0x01, 0x03, 0x13, 0x1C, 0x41 and 0x51 (DiagnosticsModel.swift:60-75) — all of which several emissions ECUs answer with different bitmasks.

*Failure:* The G70 answers Mode 01 with three modules. If the transmission ECU's line is first in the reply, `ReadinessReport(data:)` decodes the TCM's monitor bitmask: byte C has almost nothing supported, so `applicable` is nearly empty, `incomplete` is empty, and the screen prints "Ready for inspection" while the engine ECU still has Catalyst and EVAP incomplete. Bus/adapter ordering is not fixed between reads, so the monitor list also changes size from one read to the next — the symptom recorded as open task #9. Per ISO 15031-5 / J1979 the tester must combine responders: OR the support bits, and treat a monitor as complete only when complete in every ECU that supports it. Taking one arbitrary responder does neither. The same `.first` also decodes `oxygenSensorsPresent`, `fuelSystemStatus`, `fuelType` and `obdStandard` from whichever module spoke first.

*Suggested fix:* Return all responders rather than one, and validate each: keep only responses whose `payload.first == 0x41` and whose next byte equals `pid`. Prefer the engine header (`expectedResponseHeader(for: "7E0")`) the way `read(_:)` does for single-value reads, and for PID 0x01/0x41 hand the full set to `ReadinessReport` so it can OR the support bytes (B/C) and AND the completion across responders.

### An inconclusive deep-scan sweep is rolled back in memory but never persisted, so the module stays permanently "Scanned"

`App/ScanModel.swift:309` · **high** · persistence

`sweep` ends with `onProgress()` (ScanModel.swift:229) and `absorb` calls it every 64 identifiers (line 278) — that closure is `{ stored = model.encoded() }` (DeepScanView.swift:243), so by the time the sweep ends `@AppStorage("udsScanProgress")` already holds a cursor sitting at the end of the address space. `finish(target:)` then rolls the sweep back with `working.discard(...)`, calls `publish(force: true)` (line 330) so the in-memory `progress` is corrected — but never calls `onProgress()`, so the stored blob is never rewritten. `ScanProgress.discard`'s own doc states the exact failure this is supposed to prevent: "Without this an inconclusive run is indistinguishable from a completed one: the cursor sits at the end of the address space, the module reads as fully scanned, and the button that would retry it is disabled" (UDSScan.swift:251-255). That justification is factually wrong as wired up — the rollback does not survive the session.

*Failure:* A Service 22 sweep of fwdRadar runs and every probe comes back `.silent` (adapter dropped, gateway not routing). `onProgress()` has already written cursor["fwdRadar/22"] = 0x10000 to AppStorage. `finish` discards it in `working`, the button re-enables, and the user closes the sheet. `DeepScanView` holds `@State private var model = ScanModel()`, so reopening the sheet builds a fresh model and `.task { model.load(from: stored) }` (DeepScanView.swift:62) restores the un-rolled-back blob. `remaining(for:)` returns 0, the button reads "Scanned" and is `.disabled(...)` (DeepScanView.swift:246-249). The module can never be re-swept without the global Reset, and the log line claiming the sweep was "discarded as inconclusive" is false. Stopping mid-run hits the same hole: the Stop handler runs `stored = model.encoded()` synchronously (DeepScanView.swift:237) before the cancelled task reaches `finish`.

*Suggested fix:* Give `finish` the `onProgress` closure (store it on the model in `start`, or pass it through the task) and call it after the `discard` loop, before or alongside `publish(force: true)`, so the rolled-back `working` copy is what reaches `@AppStorage`.

### Multi-frame reads (VIN, calibration ID, ECU name, DTC lists) inherit the single-frame adaptive timeout and are silently dropped

`Sources/KoboldCore/ELM327/ELM327Driver.swift:638` · **medium** · timeout

`readVehicleInfoText`, `readRawPID` and `readTroubleCodes` all call `send(...)` with no `timeout`, so `sendRaw` falls back to `timing.current` (line 743). `AdaptiveTiming` converges that window on twice the observed single-frame round trip (`recordSuccess` floors `next` at `roundTrip.scaled(by: 2.0)`, AdaptiveTiming.swift:43-50, min 32 ms), driven entirely by the dashboard's one-frame Mode 01 polls. A Mode 09 VIN or a multi-code Mode 03 reply is several CAN frames and several BLE notifications longer than that. Every other long-reply call site in this file was given an explicit, generous window — `identifyModules` passes `timeout: .milliseconds(1200)` (line 466) and `scanIdentifiers` retries silence at `.milliseconds(1_500)` with a comment explaining exactly this hazard (lines 541-549) — so the omission here is inconsistent with the file's own reasoning, not a deliberate choice.

*Failure:* Dashboard polling at 30 ms single-frame round trips drives `timing.current` to ~60 ms. The user opens Diagnostics; `readVehicleInfoText(pid: 0x02)` sends `0902`. The reply is a 20-byte ISO-TP message — first frame plus two consecutive frames, ~100 bytes of ASCII with `ATH1`/`ATS0`, six 20-byte BLE notifications at a 30 ms connection interval, so ~180 ms before the `>` prompt lands. `awaitResponse` times out at 60 ms and throws. `sendLocked`'s `retries: 1` does not help: the retry loop only re-sends on `reply.isTransient` (line 301) and a thrown timeout never reaches it. `DiagnosticsModel.text(from:pid:label:)` catches the error and does `unavailable.insert("VIN")`, so the screen reports the car does not publish a VIN when it published one 120 ms too late. Same for calibration ID, ECU name and any Mode 03 reply with more than two codes.

*Suggested fix:* Give the long-reply reads an explicit floor, as `identifyModules` already does: `try await send(command, timeout: .milliseconds(1500), retries: 1)` in `readVehicleInfoText` (line 638) and `readTroubleCodes` (line 618); or add a `multiFrameTimeout` to `AdapterDescriptor` and use `max(timing.current, descriptor.multiFrameTimeout)` for these call sites.

### identifyModules leaves the previous module's ATCRA receive filter in place for any module with no receive address

`Sources/KoboldCore/ELM327/ELM327Driver.swift:460` · **medium** · protocol-state-leak

The loop sets `ATCRA <receive>` only when `module.receive` is non-nil, but never clears a filter set by a previous iteration. `ATSH` is rewritten every pass, so the transmit address is correct, while the CAN receive filter still points at the previous module's response address — which discards the reply the current probe is waiting for. The comment on the `ATCRA` call names the reason the filter is set but not that it must be unset; the only reset (`ATAR`, line 486) happens after the whole loop.

*Failure:* `probeableModules` is a stable sorted list built from `ecuHeaders` where `probe == true`, and `ECUHeader.receive` is optional. Add a probeable module with no receive address — say `"bcm": {"transmit": "770", "probe": true}` — and it sorts after `absEsc` (transmit 7D1, receive 7D9). The `absEsc` iteration issues `ATCRA 7D9`; the `bcm` iteration issues `ATSH 770` and then `22F100`, but the adapter is still filtering to 7D9, so the BCM's reply from 778 is discarded and the probe returns `NO DATA`. A fitted module is reported as not present, permanently, with no log line — and `identifyModules` never throws, so nothing surfaces the fault.

*Suggested fix:* Reset the filter on every iteration rather than only setting it: replace the `if let receive` block with `_ = try await sendLocked(module.receive.map { "ATCRA \($0)" } ?? "ATCRA", retries: 0)`, so a module with no receive address explicitly clears the previous one.

### stop() during the window before adopt(transport:) leaves an orphan 12-second BLE scan nothing can reach

`App/SessionModel.swift:268` · **medium** · lifecycle

`adopt(transport:generation:)` silently drops the transport when the generation is stale (SessionModel.swift:571-574), and `runAdapter` neither checks the result nor `Task.isCancelled` before calling `transport.connect()`. The comment at lines 264-267 claims registering the transport before connecting is what makes the 12-second scan reachable by `stop()`; in the stale case it is not, and `BLETransport`'s cancellation handler does not cover the gap either. `withTaskCancellationHandler` runs `onCancel` *before* `operation` when the task is already cancelled, and `onCancel` does `queue.async { guard self.pendingConnect != nil else { return } }` (BLETransport.swift:137-138) — that block is enqueued on the serial queue ahead of `performConnect`'s block, which is the one that sets `pendingConnect` (line 170). So the handler sees nil, no-ops, and the scan starts unopposed.

*Failure:* App launches; `KoboldApp`'s `.task` calls `session.startAdapter()`. Before the detached body reaches `await adopt(transport:generation:)` — one Task hop plus `AdapterRegistry()`, descriptor construction and `BLETransport.init` — the user opens the status pill and picks "Demo mode". `stop()` bumps `generation` and cancels `runTask`, but `activeTransport` is still nil, so there is nothing to disconnect. `adopt` then drops the new BLETransport on the stale generation. `connect()` finds the task already cancelled, `onCancel` fires first and finds `pendingConnect == nil`, and `performConnect` proceeds to build a second `CBCentralManager` and scan for the full 12 seconds with no reference anywhere in the app. If that orphan wins the discovery race it resolves `connect()`, `driver.start()` runs `ATZ` against the physical adapter, and — if the user then picks "Connect to adapter" again — it resets the dongle in the middle of the live session's init sequence. That is the exact failure BLETransport.swift:128-133 says the cancellation handler prevents.

*Suggested fix:* Make `adopt` report whether it took ownership and bail out when it did not: `guard await adopt(transport: transport, generation: generation) else { await transport.disconnect(); return }`.
